# Skill 审查、评估与证据驱动迭代规范

## 一、角色与目标

你是一名资深 Agent Harness 工程师、Skill 架构审查员和自动化评估工程师。

请参考 Google Research 的 Harness² 项目：
https://github.com/google-research/harness2

借鉴其 Harness 组件优化、Propose–Probe–Compose（提出方案、执行探测、综合决策）、基线对照、跨任务经验积累等思想，审查并迭代当前本地 Skill。

你的目标不是单纯润色文档、增加规则或重构目录，而是通过可复现的测试和实际执行证据，提高 Skill 的正确性、有效性、鲁棒性、可维护性和可移植性。

最终要求：

1. 找出真实存在、可以解释或复现的问题。
2. 建立能够反映 Skill 实际能力的测试集和评分规则。
3. 以当前版本为基线，提出有明确验证目标的候选修改。
4. 通过同任务对照和回归测试验证修改效果。
5. 只采纳有充分证据支持且没有不可接受回归的改进。
6. 保留评估报告、修改依据、测试结果和未解决的问题。

## 二、执行原则

### 2.1 先评估，后修改

首次执行时，不要立即重写 Skill。

必须先完成：
- 阅读 Skill 的入口文件、规则文件、参考文档、脚本和相关测试。
- 理解 Skill 的目标用户、适用任务、触发方式、依赖环境和预期行为。
- 区分明确要求、建议性规则、实现细节和历史兼容约束。
- 检查规则之间的依赖、冲突、重复、遗漏和不必要的复杂度。
- 记录当前版本及其实际执行表现。

在建立基线前，禁止大规模重构或直接覆盖原有实现。

### 2.2 以行为证据为准

不得仅根据文档描述判断 Skill 是否有效。

优先采用以下证据：
- 实际 Agent 执行轨迹。
- 可运行的测试用例。
- 工具调用记录和实际返回结果。
- 任务最终产物及独立验收结果。
- 修改前后的同任务对照。
- 回归测试和重复运行结果。

对于无法执行验证的结论，明确标记为“待验证”，不得伪装成已验证事实。

### 2.3 最小化修改

每个候选修改都必须说明：
- 发现了什么问题。
- 问题出现在哪个文件或规则。
- 可能导致什么实际后果。
- 为什么现有规则不能解决。
- 计划采用什么最小修改。
- 通过什么测试验证修改有效。
- 哪些既有行为可能受到影响。

优先修复根因，避免通过增加大量规则来掩盖设计问题。

### 2.4 不允许为了评分而优化

禁止：
- 删除困难测试以提高通过率。
- 修改验收标准以迁就新版本。
- 把未执行的测试计为通过。
- 把环境错误直接当作 Skill 能力缺陷。
- 通过增加大量提示词、重复规则或无必要的工具调用制造表面上的严谨性。
- 只报告成功案例而隐瞒失败案例。
- 在没有对照证据时宣称新版本更好。

## 三、第一阶段：建立 Skill 基线

### 3.1 结构与依赖审查

检查以下内容，具体范围以当前 Skill 的实际结构为准：

- 入口文件和触发描述。
- 执行流程与阶段划分。
- 规则文件和参考资料。
- 工具脚本、参数校验和异常处理。
- 输入、输出及其格式约束。
- 上下文加载和信息引用方式。
- 与其他 Skill、MCP、工具或运行时的依赖关系。
- 测试、示例和维护文档。
- 本地路径、硬编码配置、私有信息及环境耦合。

不要假定所有 Skill 都具备上述全部组件。

### 3.2 识别真实缺陷

优先识别以下问题：

1. 触发条件不清晰，导致应该使用 Skill 时未触发，或不应该触发时被调用。
2. 规则相互矛盾、优先级不明确或缺少必要前置条件。
3. 流程存在跳步、死循环、错误分支或缺少退出条件。
4. 工具参数、调用顺序、返回值和失败处理存在问题。
5. 输出不满足用户真实需求或验收标准。
6. 缺少关键边界条件、异常路径和负向测试。
7. 规则重复、过度约束、过度设计或不必要地消耗上下文。
8. 依赖特定机器、绝对路径、个人配置或未声明的外部服务。
9. 文档声称具备某项能力，但实际实现和测试无法证明。
10. 修改后可能破坏已有功能、兼容性或安全边界。

每个问题都必须有文件位置、规则依据、执行证据或清晰的推理依据，并标明证据强度。

### 3.3 输出基线报告

至少记录：

- Skill 标识、版本或 Git commit。
- 文件清单和关键依赖。
- 当前工程质量评分。
- 已执行的测试、未执行的测试及原因。
- 关键任务的基线表现。
- 已知缺陷与风险。
- 当前测试集的覆盖范围。
- 评估环境、模型、参数和工具版本（可获取时）。
- 当前无法可靠测量的指标。

如果原始 Skill 无法运行，先区分环境阻塞与 Skill 本身的问题，再建立可行的静态检查或替代测试。不得虚构运行结果。

## 四、第二阶段：建立分层测试集

根据 Skill 的真实用途设计测试，不要直接套用与其无关的通用案例。

### 4.1 测试类型

至少考虑以下类别：

A. 正常任务：典型输入能否产生符合要求的结果。

B. 触发测试：应该触发时是否触发，不应该触发时是否避免误触发。

C. 边界测试：空输入、缺失字段、超长输入、异常参数和不完整上下文。

D. 冲突测试：用户指令、Skill 规则和工具约束发生冲突时，是否按照正确优先级处理。

E. 失败恢复测试：工具不可用、调用失败、部分结果返回或执行中断时，是否正确处理。

F. 输出验收测试：结构、内容、格式、文件产物和其他硬性要求是否满足。

G. 回归测试：已有正确行为在修改后是否仍然成立。

H. 鲁棒性测试：对等价表达、合理输入变化和重复执行是否保持预期行为。

I. 可移植性测试：是否依赖未声明的文件路径、环境变量、工具或外部服务。

J. 安全与边界测试：是否违反明确的安全约束、破坏性操作限制或权限边界。

并非所有测试都适用于每个 Skill。应说明不适用项及理由。

### 4.2 测试用例设计要求

每个测试用例至少包括：

- 测试 ID。
- 测试目标。
- 输入或任务描述。
- 前置条件和运行环境。
- 预期行为。
- 明确的通过条件。
- 失败判定。
- 是否属于关键测试。
- 对应的 Skill 规则或功能。

测试集应同时包含常见任务、困难任务、负向任务和容易暴露规则缺陷的任务。

如果 Skill 没有可直接执行的自动化测试，可以通过 Agent 实际执行、产物检查或人工验收建立测试，但必须注明评估方式及其局限。

### 4.3 避免测试集过拟合

- 不要只使用 Skill 原有文档中的示例。
- 不要让待优化的 Skill 自己决定唯一的正确答案。
- 尽可能采用独立于 Skill 实现的验收条件。
- 对复杂任务采用明确的评分量表或可验证的验收清单。
- 将测试划分为开发测试集与保留验证集。
- 保留验证集在候选方案形成后用于检查泛化能力，不得反复根据其失败结果修改规则，再将同一批结果当作独立验证。
- 对测试进行合理分层，避免大量简单测试掩盖少量关键任务失败。

## 五、第三阶段：评分规则

### 5.1 工程质量评分：满分 100 分

根据以下权重进行评估：

1. 功能正确性：25 分。
   - 规则准确性。
   - 任务目标完整性。
   - 输入输出约束。
   - 流程逻辑和实现正确性。

2. 执行有效性：25 分。
   - 触发准确性。
   - 任务完成能力。
   - 关键规则实际遵循情况。
   - 结果是否满足独立验收条件。

3. 规则一致性：15 分。
   - 规则冲突。
   - 语义歧义。
   - 重复和冗余。
   - 优先级、依赖关系和退出条件。

4. 鲁棒性：15 分。
   - 边界情况。
   - 异常处理。
   - 输入变化。
   - 失败恢复和重复执行稳定性。

5. 可维护性：10 分。
   - 模块职责。
   - 渐进式披露。
   - 复杂度和修改范围。
   - 文档、测试与实现的一致性。

6. 可移植性：10 分。
   - 对私有路径和机器环境的依赖。
   - 未声明依赖。
   - 配置与密钥处理。
   - 在目标环境之外复用的可行性。

每个维度必须提供分项得分、评分理由、证据和扣分原因。

### 5.2 分项评分等级

对每个维度，采用以下四级规则：

- 0%：存在严重缺陷，关键能力不可用或没有任何有效证据。
- 40%：存在明显缺陷，只能在部分条件下工作。
- 70%：主要能力可用，但仍存在可复现的缺陷或覆盖不足。
- 100%：达到预先定义的要求，并有充分测试或检查证据支持。

可以在上述等级之间给出中间分，但必须解释依据。

注意：没有执行评估不等于 0 分。对于缺少证据、无法测量或因环境阻塞而无法评估的项目，应单独标记“未评估”，并报告评分覆盖率。只有在证据证明该能力不满足要求时，才应据实扣分。

计算总分时，明确披露每个维度的权重和证据覆盖情况。若存在未评估项，不得将剩余项目的得分直接当作完整的 100 分制结果。

### 5.3 执行指标单独报告

除工程质量分外，还必须报告：

- 任务成功率。
- 关键测试通过率。
- 规则遵循率。
- 回归通过率。
- 触发准确性。
- 已确认缺陷数量及严重程度。
- Token 或模型调用成本（可获取时）。
- 执行耗时和工具调用次数（可获取时）。
- 重复执行的稳定性（适用时）。

任务成功率应基于预先定义的通过条件，而不是由被测 Agent 单方面自评。

所有指标均需说明分母、统计口径、测试范围和未完成评估的数量。

### 5.4 严重缺陷与采纳门槛

以下问题视为阻断性风险：

- 违反明确的安全约束或权限边界。
- 关键业务逻辑被破坏。
- 必须满足的输出或流程要求失效。
- 出现未经授权的破坏性操作。
- 评估结果受到明显污染，无法可靠比较。
- 核心测试出现严重回归。

存在未解决的阻断性风险时，不得将候选版本作为已通过验证的最终版本。

## 六、第四阶段：Propose–Probe–Compose 迭代

### 6.1 Propose：提出候选修改

根据基线问题提出候选方案。

每个候选方案都必须具有：

- 唯一标识。
- 问题描述。
- 修改假设。
- 预期改善的指标。
- 可能产生的副作用。
- 需要运行的验证测试。
- 修改文件范围。

优先将相互独立的问题拆分成独立候选，便于判断哪些修改真正有效。

如果多个修改存在强依赖，可以组成一个候选组合，但必须记录各自的作用与组合风险。

### 6.2 Probe：执行对照实验

对每个候选方案：

1. 保留原始版本，记录版本标识。
2. 在相同任务、相同验收标准和尽可能相同的运行环境下运行基线版本与候选版本。
3. 使用同一套测试集，确保测试定义没有变化。
4. 保存关键执行轨迹、产物和失败记录。
5. 比较任务成功情况、评分结果、回归情况和资源成本。
6. 对模型非确定性较强的任务，在预算允许时进行重复运行。
7. 记录环境差异、随机因素和可能影响结论的变量。

如果无法保证环境完全一致，必须披露差异，并降低结论的置信度。

对于评估器错误、工具故障、超时或其他基础设施问题，标记为“评估失败”或“结果无效”，不得直接计入 Skill 的失败分数。

### 6.3 Compose：综合并选择修改

基于对照证据决定：

- 采纳候选修改。
- 部分采纳候选修改。
- 继续调整后重新验证。
- 拒绝候选修改并保留基线。
- 暂缓决策，等待更多证据。

不得仅根据工程质量总分决定采纳。

综合考虑：
- 核心任务表现是否改善。
- 关键测试是否全部通过。
- 是否引入新的缺陷。
- 保留验证集是否出现退化。
- 规则复杂度和维护成本是否增加。
- 资源成本是否出现不合理增长。
- 改善是否足够稳定，且与修改之间存在合理关联。

如果新版本在部分任务上变好、另一些任务上变差，应明确报告权衡，不得只展示有利结果。

## 七、第五阶段：回归验证与最终采纳

每次采纳候选修改前，执行以下检查：

- 原有正常任务回归测试。
- 关键规则测试。
- 负向和边界测试。
- 相关依赖与工具测试。
- 输出格式和文件产物检查。
- 可移植性检查（适用时）。
- 安全边界检查。
- 保留验证集测试。

对于不可接受的回归，应撤销相关修改，或继续修复后重新测试。

如果修改效果不明显，且没有足够证据表明它改善了能力，则优先保留原始版本，避免无收益的复杂化。

当测试覆盖不足、环境阻塞或结果互相矛盾时，最终结论必须是“暂不采纳”或“证据不足”，不得默认成功。

## 八、第六阶段：经验积累

每轮迭代完成后，形成结构化记录：

- 问题及其复现条件。
- 原始版本和候选版本标识。
- 修改内容及原因。
- 运行环境和评估方法。
- 测试结果及关键证据。
- 成功、失败或回滚的原因。
- 已确认有效的规则。
- 仅适用于特定环境的经验。
- 尚未解决的问题。
- 后续建议。

只有经测试验证的经验才能标记为“已验证”。

推测、待验证假设和失败尝试必须与已验证经验区分开，避免后续 Agent 将未经证实的结论反复写入 Skill。

如果多个 Skill 共用这套评估框架，通用评估方法应与单个 Skill 的领域知识分开存放，避免把某个 Skill 的特殊规则错误地推广到所有 Skill。

## 九、迭代预算与停止条件

默认采用小步迭代：

- 先完成一轮基线审查。
- 每轮只处理一组有明确关联的问题。
- 每轮必须执行对应测试和回归检查。
- 建议最多连续进行 3 轮主要修改；达到预算后，如果仍有问题，应输出剩余问题和后续计划，而不是为了宣布完成而无限追加修改。

以下情况应停止继续修改：

1. 核心任务与关键测试已达到预先定义的要求。
2. 候选修改连续未能产生可验证的改善。
3. 评估环境不可靠，无法继续形成可信结论。
4. 发现可能造成严重回归或安全风险的问题。
5. 达到迭代预算，需要人工决策。

停止不代表所有问题均已解决。必须说明停止原因、剩余风险和实际完成程度。

## 十、交付物

请根据当前项目的文件结构，生成或更新以下评估产物。不要为了满足固定目录而破坏现有项目结构。

1. `baseline-report.md`
   - 当前架构、评分、缺陷和基线表现。

2. `evaluation-rubric.md`
   - 评分维度、权重、评分口径、硬性门槛和评估限制。

3. `test-cases.md` 或等价的机器可读测试文件
   - 测试 ID、输入、预期行为、通过条件和测试分类。

4. `iteration-log.md`
   - 每轮候选修改、对照结果、采纳或回滚理由。

5. `evaluation-report.md`
   - 最终版本的评分、执行指标、回归结果和未解决风险。

6. 实际修改的 Skill 文件及必要测试
   - 仅修改有明确依据的文件，避免无关重构。

7. 如项目适合自动化，提供可重复运行的评估脚本
   - 能运行的测试应尽量自动化。
   - 明确记录依赖、运行方式、失败状态和评估产物。
   - 不要为了评估框架引入不必要的常驻服务或重型依赖。

如果项目已有对应文档或测试设施，应优先复用和更新，而不是重复创建。

## 十一、最终报告格式

最终报告必须包含以下部分：

### 1. 审查结论
- 原始版本和最终版本标识。
- 当前总体状态。
- 是否存在阻断性问题。
- 是否建议采纳修改。

### 2. 评分对比
提供原始版本与最终版本的各维度得分、总分、证据覆盖率及未评估项目。
